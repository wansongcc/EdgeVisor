## 本轮新增修复

- `4a1bc1b`：Vulkan 计算只在线程 0 执行，按 CPU 核数启动执行线程会增加忙等屏障。默认单机和单设备 PP 阶段改为 1 个执行线程；TP 阶段沿用按同步 peer 数调节线程的逻辑，显式 `--nthreads` 优先；CPU/CUDA 默认线程策略保持原有行为。CLI 帮助和 README 同步更新。
- `c0c176a`：KV 接收端确认完成时，其他 worker 的同 token 性能/采样帧可能仍在流中。迁移提交检查先缓存这些完整帧，再读取原有 ACK，避免把帧头当成 ACK。检查保持每 worker 一秒期限，部分头、部分 payload 和无响应均受该期限约束；非法 ACK 仍报错。没有改变线上 ACK 格式。

旧默认 16 线程在空闲 RTX 上仍于 90 秒外部期限退出 124。因此，前一轮的共享 GPU 任务不是全部超时的唯一原因。相同二进制显式单线程对照通过；调整默认策略后，无需用户追加线程参数即可通过。

五机顺序为 nx1→nx2→rog→nano2→nano1，初始自动比例为 `1@22*1@3*1@1*1@1*1@1`。ROG worker 实际使用 RTX/Vulkan 默认 1 线程，其余使用 CUDA 默认线程。

表中 ROG 单线程对照使用旧 `a7dfa14`；线程修复后的单机长测、CPU 对照和首轮四台 Jetson 复测使用 `4a1bc1b`；最终五台默认短测、五机流水线、自动模式和定向迁移均使用 `c0c176a`。后者只新增迁移 ACK 处理，没有再次运行单机长测或 CPU 对照。

修复前五机 `--auto` 在两次反向迁移后，于 pos=39 附近出现 `Invalid ack packet` 并退出 1，原始日志保留为 `five_resumed_auto96_before_ack_fix*`。修复后的自然 `--auto` 用例完成了 1→0 的迁移，但没有执行提交探测路径；不能仅用它证明 ACK 修复已实机覆盖。

因此增加定向用例：保持 `--auto` 与正常帧协议，设置 `DLLAMA_TPOT_MIN_PP_GAIN_MS=1000000` 抑制自发迁移，在观察 pos=27 后通过现有本地 UDS `set_pp_migration` 接口请求 `next_barrier`、0→1、layer 21、1 层。请求经正常 admission/JIT 检查接受，在 pos=30 迁移，真实提交检查输出 `workers_acknowledged=4 status=ok`，之后持续生成至 pos=63。每个生成位置均有五个节点的性能记录，证明提交检查没有丢弃缓冲帧。

## 限制

仅验证上述 Qwen3 0.6B Q40、设备、后端和配置，不代表 14B 或所有 Q40 模型通过。Vulkan 显式多线程仍可能显著变慢；本轮没有调整底层忙等屏障或验证 TP 线程自动调节性能。五机速度有明显波动，未写入速度表，也未用于改变调度策略。

前一轮的单 token 加入、4096/4097 容量边界、一次/重复采样超时、根及 worker 影子 KV 接管、缓存不足恢复结果仍见记录 09；本轮没有把这些旧实测改写为再次实测。只有该记录的两种同拓扑影子 KV 对照证明逐 token 一致，加入、自动迁移和重启均不作一致性保证。

原始命令、结果、控制请求和日志保存在本地 `work/acceptance_logs/`，不提交模型、凭据或日志包。
