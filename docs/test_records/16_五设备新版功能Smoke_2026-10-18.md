## 构建与单机

五台默认 GPU 构建均完成 CLI、API 和 `make check`；nx1、ROG 的纯 CPU 构建也均完成 CLI、API 和同一套检查。每次 `check` 执行 10 个模型无关测试，共七个独立构建配置。构建日志、二进制哈希和源码版本单独留存；这不表示运行了全部可选 GPU 数值测试程序。实验 Python 回归 25 项通过。

五台默认单机测试均不传 `--nthreads`、不传 `--max-seq-len`，使用 0.6B、32 steps，均生成 20 个 token 并退出 0。CUDA 线程数分别为 8/8/6/6，ROG/Vulkan 为 1；默认上下文为 4096。

## 分布式、迁移与恢复

除上述默认单机外，功能用例通常显式使用 `--nthreads 1 --temperature 0 --seed 42 --max-seq-len 512`；不能将其算作默认参数验收。五机顺序为 nx1 → nx2 → rog → nano2 → nano1。

| 场景 | 实测结果 |
| --- | --- |
| 两机显式 14/14 层 | 84 token，退出 0，无重启 |
| 两机自动速度分层 | 84 token，退出 0，无重启 |
| 四 Jetson 固定 7/7/7/7 层 | 84 token，退出 0，无重启 |
| 四 Jetson `--auto` | 84 token，退出 0；本次未产生实际迁移提交，只证明模式运行 |
| 五机固定 7/7/4/5/5 层 | 52 token，退出 0，无重启 |
| 四 Jetson 根端 0→1→0 迁移 | 两次真实提交；140 token 与同拓扑参照一致 |
| 四 Jetson 尾端 3→2→3 迁移 | 两次真实提交；140 token 与同拓扑参照一致 |
| 五机 CUDA↔Vulkan 单层往返 | 第 13 层 1→2→1，两次真实提交；92 token 与参照一致，无重启 |
| 根端 shadow KV 热接管 | token 32 完成后停止下一跳，113 token 与参照一致，无重启 |
| worker 前驱的掉线场景 | 触发已缓冲发送的保守重启，113 token 与参照一致；本轮没有证明该位置无重启热接管 |
| 未覆盖中间节点掉线 | 一次会话重启，继续完成 113 token |
| 尾节点掉线 | 一次会话重启，继续完成 113 token |
| 单 token prompt、解码前启动预留 worker | 完成从 position=0 开始的生成及实际加入，64 token，无无符号下溢挂起 |
| 尾端采样 payload 延迟 6 秒、等待预算 5 秒 | 一次超时恢复后完成 84 token |
| 重复尾端采样超时 | 达到两次重试上限后按预期退出 1，没有无限重试 |
| 4096-token prompt | 默认 4096 容量，完成 position=4095，退出 0 |
| 4097-token prompt | 超过默认容量，明确拒绝并退出 1 |

控制迁移用例不仅检查进程退出码，也核对 raw trace、实际 `ownership_committed`、迁移结果/KV frontier、逐位置 token 和参照输出。根端热接管使用单独链接的测试入口，在已完成 token 的输出处等待控制器，确保故障发生在下一次激活发送前；不改变模型、KV、采样或部署 CLI。普通突发断线另有记录，会按交付歧义走安全重启，不能算作热接管通过。

预留加入使用有可分配非尾端 donor 的有线拓扑。另一初始拓扑把 27 层放在尾端、根端仅 1 层，无法预留 donor；该控制器试次未计入加入通过项。第一轮迁移提示词在第二个触发位置前 EOS、未实际注入故障的钩子试次，以及端口/工作目录的控制器调试记录也均不计为通过。

## API、连续会话与真实工具

0.6B API 在单机、四机根采样、四机尾采样上各完成原有 20 请求 gate；五机尾采样在显式 30 秒预算下再完成 20 请求，共 **80 项请求检查通过（包含预期返回 400 的非法请求）**。另在服务启动时检查模型列表。覆盖冷热历史一致性、精确 KV frontier/前缀复用、无 session 隔离、改变前缀、非法输入/容量拒绝、请求 seed/temperature/top-p 重置及 SSE。

各配置中第一轮消耗 81 行 KV，连续请求恰好复用 81 行，随后 frontier 为 149；冷历史输出与温历史一致。被拒绝的请求没有推进有效 generation 或破坏已有 ledger。API 只绑定设备回环地址，经本轮 SSH 转发访问。

3B 自治计算器诊断在单机和四 Jetson 尾采样中各成功一例：模型自己选择并执行一次真实 calculator，再返回 `126`，没有强制动作、强制工具参数、强制答案或 JSON 修补。两轮生成维持相同运行上下文和 lineage，第二轮复用前一轮已消耗的 164 行 KV。四机例使用显式 30 秒预算；默认预算的失败例保留。只有两例协议/连续性诊断，不是任务集质量或性能统计。

## 默认配置失败与有效对照

### 五机默认自动调度未通过

`five_mixed_auto` 在现有网络下先将 ROG 作为预留设备，随后成功加入 12 行 KV。生成 10 个 token 后，在 position 22 附近执行一次 23 层的 CUDA→Vulkan 迁移；导出 529 行后出现连接失效、会话重启及启动回退，最终退出 1。没有把这一结果当作成功自动迁移。

对照 `five_mixed_auto_bounded` 显式指定初始 `7/7/4/5/5`、单次最多 1 层、冗余边界 3 层、所有参与进程的 IO/KV 等待预算 30000 ms，完成 108 token、一次真实 Vulkan→CUDA 迁移，无重启。进一步定向单层双向迁移也通过，见上表。

对照同时改变了初始分层、迁移步长、冗余及等待预算，不能据此归因到单一参数，也不能证明默认自动策略已经修复。后续应分别检查慢/暂不可达设备探测、实测与硬编码速度的可比性、大迁移准备/提交预算和失败回退。

### 默认 API 等待超时可导致进程退出

- 3B 四机尾采样首次请求：`NnPeerTimeoutException: Timeout waiting for worker control ACK`，连接关闭，API 进程退出。
- 0.6B 五机尾采样：前两轮请求成功；第三轮冷会话重放出现 `Timeout waiting for the pipeline tail sampled token`，API 进程退出。
- 保持模型和拓扑不变，将根端 `DLLAMA_KV_ACK_TIMEOUT_MS`、`DLLAMA_IO_TIMEOUT_MS` 显式设为 30000 后，两种诊断分别完成真实工具调用和完整 20 请求 gate。

当前控制 ACK/尾采样的默认预算为 5000 ms。`NnPeerTimeoutException` 继承 `std::runtime_error`，没有进入 API 服务现有异常恢复路径；增加预算是有效测试配置，**没有修复超时后的可用性问题**。后续需要合理的初始化/排队预算，以及超时后的错误响应、lineage 失效和安全的运行时恢复；不能直接复用半完成的流水线状态。

## 14B 五机能力短测

五台现有 14B 模型/分词器完整 SHA256 一致；模型头确认 Q40、40 层。先检查各机可用内存，再使用固定 `14/14/2/5/5`、`--max-seq-len 256 --steps 32 --nthreads 1` 和显式 30 秒预算，生成 20 token、退出 0，无重启。

该用例验证准备好的 14B 模型能在五机上按此配置运行。没有验证 14B 默认 4096 容量、14B 自动调度/API/热接管，也没有测试 14B 单机；不能将此短测推广成 14B 全功能验收。模型哈希检查会预热文件缓存，进程耗时不作为冷启动测量。
