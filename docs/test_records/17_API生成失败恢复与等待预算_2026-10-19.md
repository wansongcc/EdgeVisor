# API 生成失败恢复与等待预算修复（2026-10-19）

## 1. 结论与版本

本轮修复了 API 服务在生成期异常时**直接终止进程**的问题，并把固定拓扑下的 KV/control-ACK/尾采样等待预算从 5000 ms 调到 30000 ms。

- 基线分支：`refactor/experiment-foundation`，修复前尖端 `c8a08eb`，`main` 仍为 `bb97cab`。
- 代码改动：`EdgeVisor/src/dllama-api.cpp`、`app.hpp`、`app.cpp`、根 `README.md`。
- 没有修改模型、协议帧格式、调度策略或默认拓扑；没有合并 `main`。
- 本轮结论只覆盖 Qwen3 0.6B Q40 的五设备/双设备实测，不含 14B、长上下文和并发多会话。

## 2. 根因

1. **未捕获异常直接终止**：`NnPeerTimeoutException` 继承 `std::runtime_error`，但 `server()` 只捕获 `NnTransferSocketException` 和 `NnExecutorException`。生成期尾采样/控制 ACK 超时逃出请求循环后触发 `std::terminate`，日志表现为 `terminate called after throwing an instance of 'NnPeerTimeoutException'`。
2. **5 s 预算对五机冷回放不足**：五机默认 API gate 的第三个请求（cold replay）在 5 s 尾采样期限内失败；修复后实测该请求完整耗时约 7.56 s，10 次生成在 6.28–9.63 s。30 s 是 `docs/test_records/16` 已实机验证的预算。
3. **客户端写失败与 worker 故障混在一起**：HTTP 响应写失败也抛 `NnTransferSocketException`，旧循环会把它当成普通 socket 错误；若在生成路径上则可能误触发生成恢复。
4. **错误响应文案错误**：`writeJson` 对所有非 200 都写 `Bad Request`，503/500 的状态行不规范。

## 3. 改动

- **请求级错误边界**：`server()` 把 `NnPeerTimeoutException`、`NnPeerOfflineException`、`NnSessionRestartException`、其他 `NnTransferSocketException`、`NnExecutorException` 和未知异常分别映射为 503/500；先写错误响应，再抛 `ApiRuntimeRestartException` 展开整个 runtime。
- **安全重建**：`runInferenceApp` 对 `ApiRuntimeRestartException` 直接重抛，不把它误判为启动内存失败；`main()` 捕获后重建模型/网络/执行器。不会继续使用半完成的流水线。
- **HTTP 响应状态**：新增 `responseStarted/streaming/writeFailed`；非流式返回 503/500 JSON，流式在已发头后返回 SSE error 事件并正常结束 chunked body。客户端写失败只标记该连接，不再影响推理 runtime。
- **状态短语**：400/404/500/503 使用正确的 reason phrase。
- **等待预算**：`kvAckWaitTimeoutMs()` 的固定拓扑默认值改为 30000 ms；`DLLAMA_KV_ACK_TIMEOUT_MS`/`DLLAMA_IO_TIMEOUT_MS` 仍可覆盖。README 已同步。
- **重启重连**：session restart 后 worker 可能仍在 relisten；新增最多 10×500 ms 的同拓扑重试，避免把“刚重启还没就绪”误判为启动失败并重写拓扑。

## 4. 验证

### 4.1 双机强制超时恢复（nx1 root + nx2 worker）

根端设置 `DLLAMA_KV_ACK_TIMEOUT_MS=1`，发送一次普通 completion：

- 返回 `HTTP 503`，body 为 `{"error":{"code":"peer_timeout","type":"runtime_unavailable",...}}`；
- 日志出现 `API runtime restart: peer timeout...`；
- 进程未退出；等待重启后 `GET /v1/models` 恢复 200；
- 改用 30000 ms 再发 completion，返回 200 并生成内容。

### 4.2 五机默认 API gate

`api_session_gate.suite`（20 个请求，0.6B，五机固定分层）：

- 5 s 默认值：第三个 cold 请求返回 503 `Timeout waiting for the pipeline tail sampled token`，复现原故障；因为错误已转成响应，进程未崩溃。
- 30 s 默认值：20/20 通过；10 次生成耗时 6.28–9.63 s，cold 请求约 7.56 s。

### 4.3 双机掉线/重启恢复

运行中 SIGKILL worker 后立即重启：root 在 pos 22 检测到 `Socket closed`，执行 session restart、保留 worker、重放 prompt+已生成文本，最终完成 96 token（9.32 token/s），未出现 `Critical error`。本次 worker 在 root 重连前已就绪，未触发新增的 relisten 重试分支。

### 4.4 五机默认 auto 复跑

修复前同一 `five_mixed_auto` 在 pos 22 大迁移后出现 node2 掉线、node1 `PP peer offline without ready shadow cache`，随后启动回退失败退出 1。本轮复跑完成 96 token（10.20 token/s），无重启。该故障是**间歇性 peer 断连 + 启动竞态**，不是确定性超时；新增的 relisten 重试只加固启动竞态，未证明原始断连根因已消除。

### 4.5 构建与模型无关检查

`make -j8 check` 在 nx1 通过全部 10 项 C++ 检查（含 `test_pp_failover_network` 的缓冲尾帧、超时上限和 shadow KV 用例）。

## 5. 限制

- 30 s 是本地等待期限，不是 GPU 执行 watchdog；4096 token 的 cold replay 仍可能超过 30 s。超时后 API 会 503 并重建 runtime，不会挂死或复用半完成状态。
- 本轮没有验证流式请求在“已发 SSE 头之后”才失败的分支；代码路径已实现，但实机只覆盖了非流式 503 和超时后恢复。
- 默认五机 auto 的原始断连根因仍未定位；复跑通过不能证明该路径已稳定。relisten 重试是防御性加固。
- 没有做 14B、长上下文、并发多会话和 API 压力测试。
