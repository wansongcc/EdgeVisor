# 实验 A 补充：API per-stage 计时、14B 均衡与 bubble 口径（2026-10-20）

## 1. 结论

**API 生成路径现在能输出 per-token e2e 与 per-node exec/sync/bubble；14B 五机在同步 PP 下约 2.05 token/s，单纯调层数/线程到不了 3 token/s。**

- 新增 `DLLAMA_PROFILE=1` + `DLLAMA_TOKEN_TIMING_PRINT=1`：API 日志输出 `[token-e2e]` 和 `[token-prof]`，worker 的 perf packet 通过 boot packet 启用。
- 14B 配置对比：
  - 14/14/2/5/5 @1024：nano1 5 层 OOM。
  - **12/12/12/2/2 @1024**：可运行，e2e p50 **487 ms**，约 **2.05 token/s**。
  - 18/18/2/1/1 @1024：可运行，p50 487 ms，约 2.05 token/s。
  - 12/12/12/2/2 + `--nthreads 2`：p50 507 ms，更慢。
- 均衡不改变总 exec：同步 PP 把各 stage 的 exec 串行相加，root+node1 的 12 层各约 128–148 ms，ROG 12 层约 92 ms，nano 2 层约 46–69 ms；总和约 480–500 ms。**没有 pipeline overlap，单靠层数分配无法把 487 ms 降到 333 ms 以下。**
- **`bubble` 字段不是 pipeline bubble**：`LlmPerfPacket.bubbleUs` 只在 shadow/tool-window bubble 统计时赋值；普通 token 为 0。`[token-prof] bubble=0.00ms` 表示没有 shadow 准备工作，不是“pipeline 没有空闲”。论文 Fig.5 的 15 ms / 1.9 ms 无法用当前字段验证，需要单独的 stage idle 埋点。

## 2. 改动

- `dllama-api.cpp`：decode 循环记录 token wall；`forward()` 后取 `getLastPerf()`，按 `formatTokenE2eTimingLine` / `formatTokenNodeTimingLine` 打印；仅在 `DLLAMA_TOKEN_TIMING_PRINT=1` 时输出。
- `app.cpp`：
  - `profileEnabled` 增加 `DLLAMA_PROFILE=1`（root）。
  - `LlmBootstrapPacket.benchmarkEnabled` 增加 `DLLAMA_PROFILE=1`，让 worker 也启用 executor profiling 并回传 perf packet。
- README 补充 API 诊断开关。

## 3. 14B 结果

### 3.1 12/12/12/2/2 @1024（1 thread）

32-token 生成，steady-state：

| node | stage | total | exec | sync | bubble |
|---|---:|---:|---:|---:|---:|
| 0 (nx1) | 0 | 128.5 ms | 128.3 ms | 0.19 ms | 0 |
| 1 (nx2) | 1 | 255.6 ms | 126.3 ms | 129.3 ms | 0 |
| 2 (rog) | 2 | 351.4 ms | 90.4 ms | 261.1 ms | 0 |
| 3 (nano2) | 3 | 413.5 ms | 45.8 ms | 367.7 ms | 0 |
| 4 (nano1) | 4 | 476.3 ms | 61.9 ms | 414.5 ms | 0 |

- `[token-e2e]` p50 约 487 ms，p95 约 509 ms；约 2.05 token/s。
- `sync` 从 node1 开始快速累积，说明各 stage 串行等待上游；这不是 bubble，是 PP 串行化。
- `bubble=0` 不能解释为“没有 bubble”，原因见第 1 节。

### 3.2 18/18/2/1/1 @1024

- 之前 trace 的 token p50 487 ms、p95 615 ms；与 12/12/12/2/2 基本相同。
- 18 层 root/node1 的 exec 更高，但 nano/rog 层少；总 exec 相近，所以端到端不变。

### 3.3 线程

- 2 threads：p50 507 ms，root exec 144 ms、node1 148 ms，比 1 thread 略差。
- 结论：当前 CUDA/Vulkan 执行器下，增加线程没有帮助；瓶颈是同步 PP 的串行关键路径。

## 4. 对“>3 token/s”的判断

- 3 token/s 需要 e2e <333 ms；当前总 exec 约 480–500 ms，差 ~30%。
- 单纯改层数分配无法降低总 exec；可选路径：
  1. **pipeline overlap/async**：让下一 token 的 root stage 与上一 token 的后续 stage 重叠；这是 S3 的实质工作。
  2. **更小模型**：8B 单机已测 158–204 ms/token（5–6 token/s）；5 机 8B 应更快。
  3. **更多设备/更强 GPU**：当前 4 Jetson + 1 ROG 的算力上限。
- 在 B 的 pilot 里，建议用 **8B** 做主实验（>3 token/s），14B 只做少量验证；否则 14B 2 token/s 会让端到端矩阵非常慢。

## 5. 限制

- 只测了 32-token 生成，未做 p95/长上下文/多轮。
- 12/12/12/2/2 把 12 层放到 ROG；ROG 是 Vulkan，长时间热/频率行为未测。
- `bubble` 口径未改；真正的 pipeline idle 需要新增埋点（例如 stage 等待下一 token 的空闲时间），不能复用 `bubbleUs`。
- 14/14/2/5/5 和 5 层 nano 在 1024 下 OOM，说明 nano 的层数上限约 3；未系统扫 3/4 层边界。
- 没有 14B 的 B 矩阵；B 仍需独立实验。

## 6. 下一步（B pilot）

- 用 8B（5 机或单机）做主 pilot，14B 做少量核对；窗口档位 0.1/0.5/1/2/5/8/12 s。
- Arms 先做可运行的 4 个：Boundary-Defer、KV-Transfer、Replay、EdgeVisor；pre-copy/warm-spare 与 ablation 后续补。
- 扰动先做 compute clamp 与 worker removal 两类；每类 5 reps，配对同任务/同 trace。
- 主指标：任务 p95 完成时间/成功率；副指标：F2FT、p99 stall、工具窗口利用、能耗/内存。
- 先跑 1 workload × 1 扰动 × 4 arms × 3 reps 的 smoke，确认 harness 与失败语义，再扩矩阵。
