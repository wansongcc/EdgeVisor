# B pilot smoke：吞吐与故障路径（2026-10-20）

## 1. 结论

**吞吐目标达成：2 机 8B（18/18，context 1024）约 4.8 token/s（e2e 205–221 ms），是当前唯一 >3 token/s 的多机配置。但 B 的故障/接管路径还没跑通：外部 kill 的时机落在请求边界，API 在请求开始时就发现 peer 不活跃并 503，没有走 shadow 接管。**

- 2 机 8B 固定臂：~4.8 token/s。
- 2 机 8B shadow 臂：~250 ms/token（4.0 token/s），每 token 的 shadow `bubble` 约 **75–80 ms**，比固定臂慢约 22%；不是论文说的 <1% foreground overhead。
- 3 机 3B（12/12/4）shadow：~207–211 ms/token（~4.8 token/s 的 token 间隔，但生成质量差/会重复）；shadow `bubble` 约 39–51 ms/node。
- 14B 12/12/12/2/2：~487 ms/token（2.05 token/s）；3B/8B 多机反而更慢（同步 PP 串行相加）。
- 故障 smoke：
  - **末级故障按设计重启**：2 机 8B shadow 杀 node1 后 failover 报 `reason=last-stage`，API 503/restart。
  - **中间故障固定臂**：3B 3 机杀 nx2（第 21 个 token 后）→ 503/restart，episode 未完成。
  - **中间故障 shadow 臂**：3B 12/12/4 杀 nx2（第 22 个 token 后）→ 仍是 503/restart；shadow 在准备（bubble 40–50 ms/node），但根端在下一个请求开始时已发现 node1 不活跃，直接抛 `NnPeerOfflineException`，没有进入 forward 内的 failover 分支。
  - 3B 10/10/8 + shadow：nano1 在 shadow 模式 + 8 层下 OOM；12/12/4 才稳定。

## 3. 故障 smoke 细节

### 3.1 末级故障（2 机 8B shadow）

- 生成中杀 node1；根端日志：`⚡ [failover] fast-path reject deadNode=1 stage=1 reason=last-stage`，随后 `PP peer offline without ready shadow cache`，API 503/restart。
- 这是设计边界：README 明确“failed final stage uses session restart”。末级没有下一跳，shadow 不能把根端变成新的尾端。
- 因此 B 的 takeover 实验必须杀**中间 stage**，不能用 2 机拓扑。

### 3.2 中间故障（3 机 3B）

- 固定臂（10/10/8）：第 21 个 token 后杀 nx2，root 先完成第一轮生成和工具调用，随后 503/restart；episode 未完成。
- shadow 臂（10/10/8）：shadow 模式 + nano 8 层 OOM；改 12/12/4 才能启动。
- shadow 臂（12/12/4）：第 22 个 token 后杀 nx2，root 仍 503/restart；日志显示 shadow 准备工作在跑（`bubble` 39–51 ms/node），但根端在第二请求开始时已 deactivated node1，直接抛离线异常，没有进入 `forward()` 内的 failover fast-path。
- 结论：**外部 kill 的时机不可控**，而且 API 在“请求开始前已知 peer 离线”时不会尝试 shadow 接管。要验证热接管，需要：
  1. 一个确定性的“在指定 token/forward 内退出 worker”的测试 hook（不是外部 kill 竞态）。
  2. 一个 shadow readiness/frontier 查询，确保故障注入时缓存已覆盖 committed frontier。
  3. 明确 API 在 pre-existing offline peer 时是否应尝试接管；当前行为是直接 503/restart。

## 4. 对论文/ B 的含义

- **吞吐**：这套 5 设备同步 PP 上，只有 2 机 8B 达到 >3 token/s；14B 约 2.05，3B/8B 多机 1.3–2.3。B 的主矩阵用 2 机 8B 做吞吐/任务质量，takeover 用 3 机 3B 做机制验证，14B 只做少量核对。
- **准备开销**：shadow 臂每 token 多 ~45 ms（205→250 ms，约 22%），`bubble` 75–80 ms/token；这与论文“<1% foreground overhead”不一致。需要确认论文的 1% 是特定配置/异步 shadow 还是不同的计时口径。
- **故障语义**：末级重启是设计；中间 stage 的 takeover 需要确定性故障注入和 readiness 检查。当前 API 路径不覆盖“请求前已知 peer 离线”的接管。
- **B 矩阵规模**：按 1.9–4.8 token/s，episode 至少几十秒到几分钟；5 reps × 多臂会很慢。先做 2 机 8B 的 fixed vs shadow（任务质量/吞吐），再做 3 机 3B 的 middle-failure takeover（机制）。
