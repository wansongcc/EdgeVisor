# B smoke：确定性中间故障与 shadow 接管（2026-10-20）

## 1. 结论

**确定性故障 hook 已打通，shadow 接管在中间 stage 故障下可重复成立。**

- 3B 3 机（nx1 12 层 / nx2 12 层 / nano1 4 层，context 1024），在 worker node1 的 **pos=160** 确定性退出（decode 中、batch=1）。
- **固定臂**：root 检测到 node1 离线，failover 报 `partial-cover`，API 返回 503，0 个 generation，任务失败（32.8 s）。
- **shadow 臂**：同一故障点，root failover 成功：
  ```
  ⚡ [failover] fast-path deadNode=1 ejectedStage=1 targetStage=0 layers=[12,24) myNode=0 replay=1
  ```
  没有 runtime restart，继续完成 2 个 generation；**2/2 次重复均 bypass**。
- 但 episode 本身仍未完成：3B 模型在接管后重复同一个 `search_docs` 调用，没有输出 final_answer。**机制接管成立，端到端任务成功尚未证明。**

## 2. 确定性故障 hook

新增两个测试专用环境变量（worker 进程）：

- `EDGEVISOR_TEST_WORKER_EXIT_POS`：在指定 decode position 退出。
- `EDGEVISOR_TEST_WORKER_EXIT_NODE`：限定 node index（默认 1）。

触发点在 worker 的 `executor.forward()` 之前，仅当 `inference.batchSize()==1`，打印：

```
🧪 [test] worker node=1 exit at pos=160
```

然后 `std::_Exit(86)`。这模拟真实 worker 崩溃（进程消失、socket 关闭），不依赖外部 kill 的时序。代码在 `app.cpp`，nx2 已重编 `dllama`。

## 3. 结果

| arm | 故障点 | failover | 503/restart | generations | 任务完成 | wall |
|---|---|---|---|---:|---|---:|
| fixed | node1 pos=160 | `partial-cover` 拒绝 | 是 | 0 | 否 | 32.8 s |
| shadow #1 | node1 pos=160 | `ejectedStage=1 targetStage=0 replay=1` | 否 | 2 | 否（重复工具） | 129.5 s |
| shadow #2 | node1 pos=160 | 同上 | 否 | 2 | 否（重复工具） | 129.4 s |

- 固定臂的 503 发生在 32.8 s：root 收到离线，`PP peer offline without ready shadow cache`，没有 token 返回。
- shadow 臂没有 restart 标记，第一个 generation 在故障后继续完成（34.6 s），工具调用 684 ms，第二个 generation 94.2 s；模型重复工具调用，未 final。
- shadow 臂的 token 计时（故障前）约 207–211 ms/token，`bubble` 39–51 ms/node（shadow 准备开销）。

## 4. 解释

- **接管路径成立**：中间 stage 的 shadow 覆盖了 [12,24) 层；故障发生时 root 能把该 stage 从流水线 eject，并在本地/上游继续，`replay=1` 表示需要重放当前 token。
- **固定臂失败是预期**：没有 shadow，failover 只能报 `partial-cover`/`shadow-unfilled`，然后 session restart。
- **任务未完成不是接管失败**：是 3B 模型在拿到检索结果后仍重复调用工具（模型能力/提示问题）。要测端到端收益，需要换一个能 finalize 的任务/模型，或把 max_turns 提高到 3–4。
- **代价**：shadow 臂 wall 129 s vs 固定臂 33 s 失败。固定臂“快”是因为直接失败；shadow 臂付出了继续执行的时间。B 的主指标应同时看成功率与完成时间，不能只看 wall。

## 5. 限制

- 只测了 1 个故障位置（pos=160）和 1 个 workload（search）；shadow 2 次、fixed 1 次，样本很小。
- 3B 模型质量差，任务没有 final；不能从本轮得出“任务成功率提升”的结论，只能得出“故障后会话可继续”。
- 3 机 3B 的吞吐约 1.9–4.8 token/s（取决于 shadow/配置），episode 很长；B 矩阵要按这个成本设计。
- 没有无故障基线；shadow 的准备开销（bubble 39–51 ms/node）与固定臂的对比还不完整。
- `replay=1` 的语义、重放 token 数、F2FT 还没有细拆；后续要从日志/事件里补。

## 6. 下一步

1. **让任务 finalize**：提高 max_turns 到 4，或换 coding_fix_slug / 更明确的 search 提示；先在无故障下确认 3B 能完成。
2. **同任务 fixed vs shadow**：各 3 reps，记录成功率、wall、F2FT、replay token 数、shadow bubble 开销；无故障基线各 1 次。
3. **故障位置扫描**：pos=160/200/240，确认 shadow readiness 与接管率的关系；哪些位置是 `partial-cover`。
4. 再把 arms 扩到 Boundary-Defer/KV-Transfer/Replay/pre-copy；当前只验证了 full vs no-shadow。
