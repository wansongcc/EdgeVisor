# B 任务级 smoke：3B finalize 与 8B shadow 内存边界（2026-10-20）

## 1. 结论

**机制接管已成立，但任务级 fixed vs shadow 还没有跑出来；原因是模型 finalize 与 nano 内存两条约束同时卡住。**

- 3B 3 机（12/12/4）确定性故障 pos=160：shadow bypass 2/2 成功；但 3B 在 search 任务上反复调用同一个 `search_docs`，max_turns 从 2 提到 4 仍不 final（4 个 generation，348 s）。
- 8B 3 机 shadow 想解决 finalize，但 nano1 放不下：
  - 16/16/4（nano 4 层）+ shadow 16：nano1 `cudaMalloc` OOM。
  - 17/17/2（nano 2 层）+ shadow 17：nano1 仍 OOM。
- 8B 4 机**无 shadow**（10/10/8/4/4）之前可以跑；说明 shadow 模式显著增加 worker 内存，nano 的 8B + shadow 不可行。
- 8B 2 机 shadow（18/18）可以跑，但末级故障按设计重启，不能验证中间 stage 接管。

## 2. 3B finalize 失败

- 任务：search_001；max_turns=4；shadow 12/12/4；exit pos=160。
- 事件：generation 35.2 s（tool call）→ tool 731 ms → generation 93.3 s（重复 tool）→ repeated_action → generation 104.1 s（重复）→ generation 114.9 s（重复）→ 结束，final 为空。
- wall 348 s。模型看到了正确 observation（City_000123），但仍然重复同一个 query；harness 的重复提示没有让它 finalize。
- 这不是接管失败：shadow bypass 后会话继续了 4 个 generation；是 3B 指令跟随能力不足。

## 3. 8B shadow 内存边界

| 配置 | shadow | nano 层 | 结果 |
|---|---|---:|---|
| 8B 4 机 10/10/8/4/4 | 无 | 4 | 可跑（之前 heavy topk 1.3 token/s） |
| 8B 3 机 16/16/4 | 16 层 | 4 | nano1 OOM |
| 8B 3 机 17/17/2 | 17 层 | 2 | nano1 OOM |
| 8B 2 机 18/18 | 18 层 | — | 可跑，4.0 token/s；末级故障只能重启 |

- `cudaMalloc(&devicePointer, bufferSize)` OOM 发生在 nano1；host 仅 3.4 GB，GPU 7.6 GB 共享。
- shadow 模式让 worker 也启用单线程/额外缓冲；即使 2 层 8B，nano 仍不够。
- 可选路径：
  1. 3B + 能 finalize 的简单任务（calculator / coding_fix_slug），做 fixed vs shadow。
  2. 8B shadow 去掉 nano：需要第 3 个能放 8B 的设备；ROG 只有 5.5 GB 空闲盘，8B 文件 6.3 GB，放不下；除非清理 ROG 磁盘。
  3. 给 nano 换更小 context（512）或更少层（1 层），再试 8B shadow；可能仍 OOM，取决于 shadow 的固定缓冲。
  4. 用 8B 2 机 + 人为把 shadow 覆盖扩展到“末级接管”，但当前代码明确拒绝 last-stage，需要改协议。

## 4. 对 B 的含义

- B 的机制验证用 **3B 3 机 12/12/4 + 确定性故障**，已经可用；需要换一个 3B 能 finalize 的任务。
- B 的吞吐/任务质量用 **8B 2 机 18/18（4.8 token/s，无 shadow）**；它不能做 takeover，但可以作为“正常路径/质量”基线。
- 把 3B takeover 与 8B 正常路径拼成一张表是不公平的；要么统一模型，要么明确分层结论。
- 下一步优先：3B calculator 或 coding_fix 任务，先无故障确认 final，再加 pos=160 故障；fixed vs shadow 各 3 reps。
